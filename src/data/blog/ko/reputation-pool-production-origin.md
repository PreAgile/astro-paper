## 준비 상태

이 글은 **실제 프로덕션 데이터 확보 후 작성**합니다.

`reputation-pool`이 필요해진 이유를 그럴듯한 사후 설명으로 만들지 않기 위해, 현재는 결론을 채우지 않습니다. 기존 선택 방식의 성공률, 차단 유형, 회복 시간과 재사용 결과를 같은 기준으로 측정할 수 있을 때 본문을 완성합니다.

## 0. 운영에서 처음 관찰한 문제

- 어떤 리소스를 선택하고 있었는가
- 실패는 어떤 단위로 반복됐는가
- 단순 재시도와 교체로 해결되지 않은 이유는 무엇인가
- 사용자 요청과 시스템 비용에 어떤 영향을 주었는가

> 준비 중 — 실제 장애 시점과 요청 흐름을 익명화한 뒤 작성합니다.

## 1. 기존 방식과 비교 기준

- 기존 선택 전략
- 성공과 실패의 정의
- 비교 기간과 표본 수
- 리소스 공급자, 요청 종류, 시간대처럼 결과를 왜곡할 수 있는 조건

> 준비 중 — 기존 방식의 baseline을 먼저 고정합니다.

## 2. 반복해서 나타난 실패 패턴

- 한 번 실패한 리소스가 다시 선택되는 문제
- 일시 실패와 장기 실패를 구분하지 못한 문제
- 작업 종류에 따라 성공률이 달라지는 문제
- 차단 뒤 언제 다시 시도할지 결정하기 어려운 문제

> 준비 중 — 각 패턴의 발생 횟수와 대표 trace를 확보한 뒤 작성합니다.

## 3. 왜 단순한 resource pool로는 부족했는가

- round-robin과 random 선택이 기억하지 못하는 정보
- 성공·실패 이력이 선택에 필요한 이유
- 전체 평판과 작업별 평판을 나눠야 했던 이유
- block, recovery와 lease가 하나의 계약이 된 과정

> 준비 중 — 관찰된 문제와 설계 요소를 하나씩 대응시킵니다.

## 4. reputation model로 바꾼 가설

- 성공한 리소스를 더 자주 선택하면 실제 성공률이 오르는가
- 최근 실패에 더 큰 가중치를 주어야 하는가
- 격리된 리소스는 어떤 조건에서 회복시켜야 하는가
- 탐색과 활용의 비율은 어느 정도가 적절한가

> 준비 중 — 가설과 결과를 섞지 않고, 반증 가능한 문장으로 먼저 고정합니다.

## 5. 프로덕션 도입과 측정 계획

| 측정 항목            | 비교할 값                        | 필요한 이유                       |
| -------------------- | -------------------------------- | --------------------------------- |
| 요청 성공률          | 기존 선택 vs reputation decision | 판단 품질의 직접 결과             |
| 리소스별 연속 실패   | 도입 전후 분포                   | 나쁜 리소스의 반복 선택 감소 확인 |
| 격리 후 회복 시간    | block 시점부터 정상 복귀까지     | 회복 정책의 과도함·느림 확인      |
| 선택 집중도          | 상위 리소스가 차지한 요청 비율   | 좋은 리소스 과사용과 고갈 확인    |
| fallback·재시도 비용 | 요청당 시도 횟수와 latency       | 성공률 개선의 숨은 비용 확인      |

## 6. 이 글을 완성할 조건

- [ ] 비교 기간과 표본 수를 공개할 수 있다.
- [ ] 성공률의 분모·분자와 제외 조건을 설명할 수 있다.
- [ ] 기존 방식과 새 방식이 같은 트래픽 조건에서 비교된다.
- [ ] 개선된 지표뿐 아니라 악화된 비용도 함께 제시한다.
- [ ] 최소 한 개의 실패 사례와 설계 수정 과정을 코드·PR에 연결한다.
- [ ] 아직 일반화할 수 없는 범위를 명시한다.

이 조건을 만족하기 전까지 이 글은 시리즈 허브에 **운영 데이터 대기**로만 표시하며 발행하지 않습니다.
